# 설계 이력 · 아카이브

**평소에는 읽지 않아도 되는 문서다.** 이미 지나간 결정과 폐기된 모델을 기록해 두는 곳으로,
"왜 이건 없지?" 또는 "예전에 이렇게 하기로 하지 않았나?" 를 확인할 때만 본다.

현재 유효한 설계는 [`DESIGN.md`](DESIGN.md), 대원칙은 [`../CLAUDE.md`](../CLAUDE.md).

---

## 1. 원래의 프로젝트 목적 (§1)

SRT 예약 페이지를 Android WebView 에서 직접 열고, 페이지의 HTML/DOM 을 분석하여
사용자가 지정한 조건에 맞는 열차/좌석이 발견되면 알린다.
좌표 기반 클릭 매크로가 아니라 DOM 분석 기반 구조를 쓴다.

> 이 목적은 그대로 유효하다. 바뀐 것은 "사용자가 지정한 조건" 의 형태다. → 아래 3절

## 2. MVP 범위 밖으로 못 박은 것 (§3)

자동 결제 · 자동 결제정보 입력 · CAPTCHA 우회 · 로그인 자동화 우회 · 서버에서의 SRT 크롤링 ·
여러 사용자 지원 · 클라우드 계정 · Telegram 연동 · PC Extension 연동 · 백그라운드 24시간 감시.

**이 목록은 여전히 전부 범위 밖이다.** 이후 [예약하기] 버튼 클릭까지가 추가되었지만
(§19-1), 그 뒤의 좌석 선택과 결제는 사용자가 한다.

## 3. 폐기 — 조건 입력 모델 (2026-08-23, 구 §37)

초기 설계는 **앱이 구간/날짜/시간 범위/좌석 등급을 입력받아 조건으로 거르는** 모델이었다.
(구 §7 `WatchCondition`, §16~§17 조건 판정, §21 조건 설정 화면, §23 조건 저장)

| | 이전 | 이후 |
|---|---|---|
| 조회 조건 | 앱 설정 화면에 입력 → 앱이 다시 거름 | 사용자가 SRT 사이트에서 직접 조회 |
| 감시 대상 | `WatchCondition` (구간/날짜/시간/좌석등급) | `WatchSelection` = 체크한 (열차, 좌석등급) 집합 |
| 판정 | `ConditionEngine` (구간→시간→등급→상태) | `SelectionEngine` (체크한 칸이 `AVAILABLE` 인가) |
| 예약대기 | `예약대기 포함` 옵션으로 발견 처리 가능 | 항상 발견 아님 |
| 저장 | 조건을 DataStore 에 저장 | 저장하지 않음 (메모리 전용) |

**왜 바꿨나**

- 같은 조건을 사이트와 앱 두 곳에 입력하면, 어긋났을 때(역 표기 차이, 날짜 하루 차이)
  원인을 찾기 어렵다. 사이트가 이미 정답을 알고 있으므로 앱이 다시 들고 있을 이유가 없다.
- 자동으로 누르는 동작은 되돌릴 수 없다. "조건에 맞는 아무 열차" 보다
  **"이 열차의 이 칸"** 이라고 못 박는 편이 오클릭 여지가 없다.
- 사용자가 실제로 원하는 것은 대개 특정 몇 편성이지, 시간 범위 전체가 아니다.

역/날짜/시간 선택 다이얼로그와 좌석 등급 입력은 전부 삭제했다.
설정 화면에 남은 것은 감시 동작뿐이다(§23).

## 4. 개발 단계 (구 §30) — 전부 완료

| Phase | 내용 | 상태 |
|---|---|---|
| 1 | WebView + JS + Cookie + 세션 유지 | 구현 |
| 2 | DOM Parser (열차번호/출도착/일반실/특실) | 구현 (실제 사이트에서 selector 검증 필요) |
| 3 | 선택 엔진 (체크한 칸 / 예약가능) | 구현 + 단위 테스트 |
| 4 | 자동 재조회 (간격/중지/오류 시 중지) | 구현 + 단위 테스트 |
| 5 | Notification (표시/클릭 복귀/중복 방지) | 구현 |
| 6 | UI (열차 선택 / 상태 표시 / 로그) | 구현 |
| 7 | 발견 시 [예약하기] 자동 클릭 (결제 전까지) | 구현 + 단위 테스트 |

## 5. 설계안과 의도적으로 다르게 구현한 부분

| 항목 | 원설계 | 구현 | 이유 |
|---|---|---|---|
| `SrtPageParser.parse` | `List<Train>` 반환 | `PageSnapshot` 반환 | §27 의 에러 구분을 열차 목록만으로는 표현할 수 없다 |
| `MatchResult` | `matched/train/reason` | + `matches: List<SeatMatch>` | "발견된 좌석 N" 표시에 필요 |
| `WatchState` | 7개 | + `PAUSED`, `RESERVED` | lifecycle 일시정지와 예약 완료를 구분해서 보여주려고 |
| `ReloadScheduler` | `schedule(action)/cancel()` | `waitForNext(interval, onRemaining)` | 단일 코루틴이면 취소가 명확하고 남은 시간을 UI 에 표시할 수 있다 |
| 새로고침 | `WebView.reload()` | 조회하기 버튼 **좌표에 실제 터치** | POST 결과 페이지 reload 문제 + URL 직접 호출/합성 클릭은 차단된다 (§10) |
| `SrtJsBridge` | 파일 존재 | 없음 | `evaluateJavascript()` 결과만 쓰는 단방향 흐름. 공격면도 작다 (§14) |
| 감시 조건 | `WatchCondition` 입력 | `WatchSelection` 체크 | 위 3절 |
| 예약대기 | 발견 여부 선택 옵션 | 항상 발견 아님 | 사용자가 고른 것은 [예약하기] 버튼이다. 대기 신청은 성격이 다르다 |
| 첫 사이클 | reload 후 분석 | 현재 화면 즉시 분석 | 사용자가 이미 조회 결과를 열어둔 상태에서 시작한다 |

## 6. 향후 로드맵 (구 §36)

1. 좌석 위치(호차 / 창가·통로) 분석 — §18
2. 선택 프리셋 저장 (매일 같은 열차를 노리는 경우)
3. Telegram Bot 연동 — **토큰은 앱에 하드코딩하지 않는다.** 서버를 두게 되면
   `Android → Backend → Telegram Bot` 구조로 간다
4. Foreground Service 기반 백그라운드 감시 — §25, §26, §19-3 의 한계 참조
5. PC Chrome Extension 과 `SelectionEngine` 공통화 — §32

목표 구조:

```
SRT Watcher
  PC      └─ Chrome Extension ┐
  Android └─ WebView Watcher  ┴→ Train[] → Condition/Selection Engine → Notification
  알림    ├─ Android Push
          └─ Telegram
```

## 7. MVP 성공 기준 (구 §35) — 달성

앱 실행 → SRT 접속 → 사용자가 사이트에서 조회 → 열차 선택 체크 → 감시 시작 →
무작위 간격으로 재조회 → DOM 분석 → 판정 → 좌석 발견 → 알림 → [예약하기] 클릭 →
사용자가 좌석 선택과 결제를 직접 진행.
